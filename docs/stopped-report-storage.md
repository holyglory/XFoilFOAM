# Stopped hub report storage

The hub report-storage worker copies signed transport reports for cancelled, stopped remote executions with an expired or cancelled promise, no live ingestion lease and no running attempt. This includes jobs closed for unresolved delivery. A job closed by the stale HZ reset also needs the registered dispatch's cancelled promise, its recorded operator release and authoritative lease loss, and zero active promise points. Both dispositions require the same physical stop proof and signed report checks. The ordinary GCS archiver handles reports that already meet its scientific and raw ownership rules.

When the scientific scan finds copies eligible for the ordinary archiver, it offers their signed keys to that same writer. When a later scientific receipt exists beyond the current window, the scan also checks up to 32 warm scientific keys immediately after that receipt. This gives larger cumulative reports a turn while the original cursor advances in order. Both windows use the same per-row eligibility check. The writer keeps at most two pages from distinct owners, ranked by observed PostgreSQL report bytes. On a priority turn it takes the largest waiting page belonging to a different owner from the last priority selection when one is available. Chronological discovery gets the intervening turn. The writer rechecks each signature, scientific receipt, bound raw original and current owner before publication. After a successful priority write it checks up to 32 still-warm scientific keys starting at the first selected sequence, including any remainder from a byte-limited page. Priority offers expire on restart. After a chronological publication commits, the worker records its immutable generation and final signed member in `ordinary-chronological.json` under the receipt directory. On startup the worker resumes from that member only when the configured bucket and prefix, bundle identity and canonical SQL pointer match. It starts at the beginning on a missing or invalid checkpoint and clears the checkpoint at the end of a pass so earlier owners get another turn.

In a chronological window the ordinary writer checks up to 512 warm keys. A report reaches the 32-row raw-ownership check only if its signed inventory contains scientific sources and each source has an earlier scientific receipt in that job. Missing receipts still remain eligible for future delivery and the shared storage path continues to handle pending scientific sources.

For other signed snapshots, the worker first copies and reopens a versioned manifest. Each object-valued scientific result has one immutable GCS object keyed by the SHA-256 of the exact PostgreSQL result text. A manifest preserves the original prefix and suffix surrounding the root result token. Null snapshots preserve the whole original. A generation pin includes its full decimal generation, compressed size, SHA-256 and CRC32C. The manifest also binds the dispatch, each sequence, the original PG body size/SHA, the independent application signature and the source inventory. Decimal spelling, unknown properties and Unicode round-trip exactly. Existing `jsonl` and worker `legacy-jsonl` archives keep their original formats and identities.

For a nonlatest report whose every point already appears in an earlier signed warm source with the same case and AoA, the worker may attach the verified manifest and replace the SQL body with its archived header. Historical null-result snapshots can also release once their empty inventory and progress receipt match. The worker first preserves the latest report, the first source for a point, and actual scientific and diagnostic receipt owners in SQL while it copies them to GCS. A later fair turn reopens the previously verified, generation-pinned original. With an anchor-capable serving API, the worker verifies the authenticated terminal head and stop, exact point inventory, source report, and both ordinary cloud readers before attaching that original. A missing, changed or corrupt generation, new head, active lease or changed dispatch keeps its SQL source. It can reuse the existing manifest and scientific generation without another scientific upload. A last SQL reference may release only the known protected hash used by an authenticated member, subject to references in both report tables.

## Deployment and selection

Install the forward archive-format constraint with the matching hub API and sweeper. The existing report-storage child starts the recurring service automatically on a verified hub with a configured evidence bucket. It checks the database, the serving API's advertised formats, and the actual API and sweeper readers before attaching the report. Every normal reader uses its own current generation read. Within a bounded page it can reuse an already authenticated scientific generation. HZ keeps its existing registered reader. The feature requires no additional cloud identity.

Production Compose supplies these settings.

| Setting | Default | Meaning |
|---|---|---|
| `AIRFOILFOAM_STOPPED_SHARED_REPORT_SCOPE` | `all` | Scan closed owners fairly. An execution UUID limits work to one owner. `off` pauses this service. |
| `AIRFOILFOAM_STOPPED_REPORT_ANCHOR_SCOPE` | `all` | Retire independently preserved sources once the serving API advertises anchor readback. An execution UUID limits anchor retirement to one job. `off` keeps its native fallback for the staged rollout. |
| `AIRFOILFOAM_STOPPED_SHARED_REPORT_RECEIPTS` | `/data/airfoilfoam/report-archives/shared-result-v1` | Durable, private directory on the existing results volume. |
| `AIRFOILFOAM_HUB_REPORT_API_URL` | `http://node-api:4000` | Internal address used to check the serving hub reader. |

Each turn inspects up to 32 report keys from one owner and writes at most one bounded manifest. Different owners take turns. Within each owner, a cursor on the existing signed point-source index alternates with the ordinary sequence cursor so large scientific reports progress even behind a long prefix of null status snapshots. The reader caps each report and scientific result at 64 MiB of original text and each page at 128 MiB of reconstructed reports. Larger originals remain intact and produce an explicit error. Runtime role, ownership, signature, source, object or reader disagreements preserve the SQL form. A confirmed complete frontier sleeps between checks and resumes on changes to the signed report/progress frontier or scientific/diagnostic receipts.

## Receipts and recovery

The worker persists a verified page receipt before pointer attachment and commits the archive member rows, compact header and reference release together. A crash before attachment leaves the original in SQL. A completed read retains only immutable member identity, so an earlier request timeout cannot cancel a new restoration. The ordinary writer restores each cold scientific receipt owner in full and matches its signed point, case and AoA. For up to eight recently checked shared-report owners it retains those matched point identities. Before reusing one it reopens the exact GCS manifest and scientific generation, reconstructs the original PostgreSQL byte count and SHA, and checks the catalogue pointer on both sides of the read. A new point or changed coordinates require full validation, and an unavailable generation leaves the dependent copy warm. The original point, raw upload, and scientific receipt ownership checks still apply. A restart after attachment follows the actual catalog rows. Content-addressed result uploads use create-only generation preconditions. A concurrent writer reopens the existing generation and verifies its exact original; a missing or corrupt dependency fails the operation.

Under each execution directory, `verified/` holds the original proof with result and manifest pins, `receipts/` holds page outcomes, and `windows/` and `cursor.json` record bounded progress. `totals.json` reconciles verified distinct generation bytes, members with actual SQL pointers, and the original versus current report-field sizes. SQL reference sizes and any actually deleted protected result values are measured separately. A local SQL release measurement counts only if its exact generation and all its canonical member pointers committed. RSS is recorded in bytes. SQL value reduction, live protected payloads, unique cloud bytes and operating-system allocation are different measurements.

The service creates no scientific, diagnostic or raw custody receipt, updates no lease or promise, and publishes no coefficients or fits. Legitimate late transfers still go through the existing registered evidence endpoints.

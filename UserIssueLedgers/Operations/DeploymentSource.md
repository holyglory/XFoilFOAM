# User Issue Ledger: Operations / deployment source

| ID | Applies to | Mistake pattern | Required behavior | Prevention and verification |
| --- | --- | --- | --- | --- |
| UIL-OPERATIONS-DEPLOYMENT-SOURCE-001 | Production branch promotion and visible admin behavior | Deploying a divergent recovery branch removed previously delivered remote-solver health from the production Health page even though the remote solver remained healthy. After the fleet view was restored, its remote build label still stayed pinned to the solver's original registration because recurring heartbeats omitted the current deployed build. | Production releases come from `master`. A candidate that is not a descendant of the currently deployed source must be explicitly reconciled against that source, and previously delivered operator-visible health behavior must not disappear silently. Every authenticated remote heartbeat reports the currently running build so preserved registrations cannot leave stale deployment provenance in Health. | Before promotion, compare the candidate and deployed source revisions, run the focused remote-fleet API/UI regressions, request the exact Health route through a browser-equivalent surface, and verify both production roles report the promoted `master` revision. A heartbeat regression changes the configured build after registration and proves the hub-visible build label follows it without credential rotation. |
| UIL-OPERATIONS-DEPLOYMENT-SOURCE-002 | Manual production source staging | Staging directly from a development checkout carried ignored cache, build-metadata, and local-tool files into a release while labeling it with the correct Git revision. | Every manual production payload is materialized from the exact pushed `master` Git tree in a fresh directory; working-tree-only and ignored files never enter the sealed source. | Generate and verify the deployment manifest inside the clean Git export, then require both roles to report the same revision, source-tree hash, and file count after promotion. |
| UIL-OPERATIONS-DEPLOYMENT-SOURCE-003 | Repository branches and worktrees | Long-lived detached worktrees accumulated production fixes, tests, and operational decisions outside `master`, obscuring which source was authoritative and delaying deployment. A new hotfix worktree repeated that fragmentation after the user asked for one maintainable repository state. | Do not create additional worktrees. Commit and merge completed work directly into `master`; immediately consolidate and remove every existing auxiliary worktree without discarding dirty files. Production deploys are sealed exports of the resulting pushed `master`. | Before production work, require `git worktree list` to contain only the main checkout and require `master` to contain every preserved worktree commit. Verify the main tree, tests, pushed revision, and both deployed manifests before reporting completion. |

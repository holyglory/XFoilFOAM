# User Issue Ledger: Operations / storage capacity

| ID | Applies to | Mistake pattern | Required behavior | Prevention and verification |
| --- | --- | --- | --- | --- |
| UIL-OPERATIONS-STORAGE-CAPACITY-001 | Hub and remote-solver CFD storage | Reproducible solver working data accumulated without a hard bounded-lifecycle guarantee until the remote Docker filesystem reached 100%, PostgreSQL became unhealthy, the remote heartbeat stopped, and campaign scheduling blocked. A terminal remote job with only rejected points was also excluded from delivery settlement, so it never received the job-level acknowledgement required for stripping. | CFD working data is disposable and automatically reclaimed. A solver must stop admitting new work before its writable filesystem reserve is threatened, aggressively remove cancelled, failed, superseded, acknowledged, and otherwise restartable working generations, and resume only after measured headroom is restored. Valid generations are delivered first; terminal rejected points are released for a fresh promise and their job receives a reclamation acknowledgement. Canonical non-solver configuration and reconnect credentials remain preserved. | Regression-test admission and cleanup with active, accepted, mixed accepted/rejected, rejected-only, terminal, acknowledged, cancelled, malformed, and orphaned jobs; include a slow or failed delivery path. In production, verify actual filesystem headroom, healthy PostgreSQL/Redis, each host's configured slot limit, fresh heartbeats, renewed promises, real solve progress, valid-generation delivery, rejected-point release, job-level acknowledgement, and post-terminal disk reclamation. |
| UIL-OPERATIONS-STORAGE-CAPACITY-002 | Deployment-host housekeeping | Stale deployment payloads and redundant database backups accumulated outside the solver volume. | Deployment payloads, Docker caches, and database backups have explicit count/age bounds; they cannot grow without limit. | A production housekeeping audit proves bounded release/staging/backup counts on both hosts and verifies its timer, last-success timestamp, and reclaim behavior without touching canonical configuration. |
| UIL-OPERATIONS-STORAGE-CAPACITY-003 | Solver admission forecasting | A deliberately conservative per-case reserve materially overstated real FAST-URANS growth and withheld usable compute despite ample measured free space. A refill loop could also reuse one pre-loop decision for multiple submissions. | Calibrate reserves from measured production p95 plus explicit headroom, reserve a realistic next-job shape, and re-evaluate measured free space plus all active future growth before every refill submission. Keep the independent measured emergency cutoff as the disposable-work backstop. | Tests use the observed eight-job FAST-URANS workload, prove its forecast admits safely, preserve measured-limit and malformed-input failure guards, and pin per-refill admission re-evaluation. Production verifies slot refill, filesystem headroom, and emergency protection. |
| UIL-OPERATIONS-STORAGE-CAPACITY-004 | Remote-solver capacity changes | Applying a changed Compose CPU limit with `compose up worker` recreated the worker before the guarded engine workflow owned the transition. The queue was logically idle but retained broker restoration state, so restarting the worker re-exposed disposable tasks. | Capacity state may be prepared only while the worker is stopped. The guarded remote engine rebuild is the sole operation allowed to create or recreate the resized worker; a disposable reset clears the dedicated broker, including unacknowledged restoration state, before that rebuild. | A capacity-change rehearsal pins the old worker container identity until the guarded recreate step, proves the dedicated Redis database is empty rather than checking only named queue lists, and verifies zero DB jobs/promises before the final worker starts. |

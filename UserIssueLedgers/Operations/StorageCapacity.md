# User Issue Ledger: Operations / storage capacity

| ID | Applies to | Mistake pattern | Required behavior | Prevention and verification |
| --- | --- | --- | --- | --- |
| UIL-OPERATIONS-STORAGE-CAPACITY-001 | Hub and remote-solver CFD storage | Reproducible solver working data accumulated without a hard bounded-lifecycle guarantee until the remote Docker filesystem reached 100%, PostgreSQL became unhealthy, the remote heartbeat stopped, and campaign scheduling blocked. | CFD working data is disposable and automatically reclaimed. A solver must stop admitting new work before its writable filesystem reserve is threatened, aggressively remove cancelled, failed, superseded, acknowledged, and otherwise restartable working generations, and resume only after measured headroom is restored. Canonical non-solver configuration and reconnect credentials remain preserved. | Regression-test admission and cleanup with active, terminal, acknowledged, cancelled, malformed, and orphaned jobs; include a slow or failed delivery path. In production, verify actual filesystem headroom, healthy PostgreSQL/Redis, the configured 8/40 slot limits, fresh heartbeats, renewed promises, real solve progress, delivery acknowledgement, and post-delivery disk reclamation. |
| UIL-OPERATIONS-STORAGE-CAPACITY-002 | Operator storage status and deployment-host housekeeping | The Admin warning conflated actual disk exhaustion with conservative future-work reservation, while stale deployment payloads and redundant database backups accumulated outside the solver volume. | Operator health distinguishes measured filesystem use from forecast admission reserve. Deployment payloads, Docker caches, and database backups have explicit count/age bounds; they cannot grow without limit. | Tests pin measured-versus-reserved status semantics. A production housekeeping audit proves bounded release/staging/backup counts on both hosts and verifies its timer, last-success timestamp, and reclaim behavior without touching canonical configuration. |

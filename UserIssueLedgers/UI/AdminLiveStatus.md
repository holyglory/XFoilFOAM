# User Issue Ledger: UI / admin live status

| ID                           | Applies to                                              | Mistake pattern                                                                                                                                                                                                      | Required behavior                                                                                                                                                                                                                                   | Prevention and verification                                                                                                                                                                                      |
| ---------------------------- | ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| UIL-UI-ADMIN-LIVE-STATUS-001 | Admin campaign hub and campaign detail scheduler status | A cached admin campaign response can retain an old global admission-fence flag after the authoritative `sweeper_state` latch is cleared, leaving a red “scheduler · safety stop” badge after scheduling has resumed. | Scheduler gating must be read as live operational state: a cleared admission fence must replace the red safety-stop badge on the next poll or page fetch. Historical fence reason is audit context only and must never independently render a stop. | Both campaign scheduler endpoints send `Cache-Control: private, no-store`; both browser fetches use `cache: "no-store"`; API regressions assert the headers and UI fetch regressions assert the no-store policy. |
| UIL-UI-ADMIN-LIVE-STATUS-002 | Admin solver, campaign hub/detail, and campaign-launch review scheduler status | A system-owned maintenance drain (`enabled=false`, inactive admission fence, retained historical fence reason) was rendered as a safety stop or a user-actionable disabled scheduler because its sanitized live maintenance state was not carried through the polling DTOs. | While `maintenanceDrainActive=true`, present a compact maintenance-drain state with no Resume/enable claim; a live admission fence still remains the red safety-stop state. Historical fence reason alone never changes the live state. | Authenticated queue and campaign projections carry only `maintenanceDrainActive` and `maintenanceDrainStartedAt`; solver/campaign/review helpers test drain precedence, live-fence precedence, and absence of a user action; UI derives all scheduler copy from those fields. |
| UIL-UI-ADMIN-LIVE-STATUS-003 | Admin active-job capacity and scheduler banners | A case-parallel engine job persisted one representative callback with one held token while its fresh worker heartbeat showed all eight active child cases; the admin UI therefore looked idle/under-utilized. Historical admission-fence provenance could also be mistaken for a current stop. | Prefer a fresh worker runtime over sibling API `/proc` and singular status callbacks; aggregate live child cases by the resolved per-case process allocation and show the real active/capacity slot count. A safety-stop label is derived only from the current `admissionFenceActive` latch. | API regression supplies `heartbeat_process_count=8`, direct count `0`, eight distinct case children, and one persisted token, then requires 8 held slots. Solver-state regression supplies historical critical-fence fields with an inactive latch and forbids a safety stop. |
| UIL-UI-ADMIN-LIVE-STATUS-004 | Admin Health and campaign-detail operational status | The UI elevated internal orphan/retry incident bookkeeping into a prominent “Solver recovery” rail with stale system-owned/retrying counts, making obsolete recovery machinery look like a primary solver stage and obscuring real capacity and work. | Do not expose a solver-recovery/audit state machine as a primary UI concept. Health leads with actual compute capacity, active work, storage, output, and direct failures; campaign detail shows its ordinary stage/progress and failed points without an internal recovery rail. | Source regressions require both user-facing surfaces to omit `SolverIncidentPanel`; rendered route verification at desktop and mobile must find no “Solver recovery” text while the compute-fleet and campaign-progress surfaces remain present. |

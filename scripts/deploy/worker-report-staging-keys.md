# Worker report staging keys

The staging key identifies an acknowledged worker report whose **stored** result is a JSON object. The job, sequence, original creation time and generated stop owner are copied verbatim. Staging queries still check the registered worker, promise, stop ownership, conflicts, leases, retries and receipts. Fetching a selected report goes through its original signed source and archive reader.

Use this option when worker staging or delivery wake polls repeatedly scan retained report metadata. Measure the existing indexed selectors first. A worker that already stays within its polling budget can continue using source-backed reads. PostgreSQL TOAST-only reclamation has its own maintenance path and does not require staging keys or index retirement.

## Install and backfill

1. Deploy migration `0218_worker_report_staging_keys.sql` before deploying callers that use the new candidate view. The migration installs the source-backed view, an empty key table and two disabled tracking triggers. It creates no checkpoint or keys. A hub-only installation has no tracking writes. The first worker backfill, or an explicit `start INSTANCE_UUID`, enables tracking for that registered instance in a short transaction using a nonwaiting source-table lock. Backfill starts after that transaction commits.
2. Run `scripts/deploy/worker-report-staging-keys.sh status` on the registered worker. The application may continue writing and using the source-backed view.
3. Run `scripts/deploy/worker-report-staging-keys.sh backfill INSTANCE_UUID 128` once per desired page. The worker instance UUID comes from its existing registration. Each invocation exits after one transaction. A busy response means retry this cursor later. A genuinely empty tail marks completion. The covering partial index must be valid and usable by PostgreSQL. The operator refuses a bootstrap plan that would scan or re-evaluate report bodies.
4. Run `scripts/deploy/worker-report-staging-keys.sh verify` after completion. The checker compares every ordered key page in both directions in one repeatable-read snapshot, including exact timestamp and stop ID. It returns the matched row count. An acknowledged insert and a first acknowledgement are tracked in the same transaction as their source row. An existing 0198 result reference proves the stored result is an object. Unreferenced sources use the original partial-index predicate on their exact key. Replayed acknowledgements and legal normalization, archival or metadata-only updates fire neither trigger. The source immutability guard preserves membership and the generated stop owner across these updates. Inspect the candidate and wake plans for the deployed worker distribution and confirm normal source hydration and receipt semantics.
5. Run `scripts/deploy/worker-report-staging-keys.sh enable INSTANCE_UUID` to repeat parity verification and atomically bind the read view to the key table. No source index is retired by enable. The `disable INSTANCE_UUID` action restores source-backed reads while all four source indexes are valid. For a full opt-out, follow it with `stop INSTANCE_UUID`. Stop takes nonwaiting locks, disables tracking, and clears the derived key table and checkpoint. A later start reproves history using a new bootstrap. A temporary worker setting change leaves already-enabled tracking intact so retained work stays consistent.

## Separate physical index retirement

Retirement requires a separately reviewed deployment decision after the revised readers are serving. Pass their exact release revision. The host wrapper takes the deployment lock, verifies the checkout manifest and compares the four caller files, migration and operator files against every running sweeper and node-api container. The SQL operator checks the exact instance, replacement indexes, active view and trigger, and all four source index definitions. It obtains a fresh complete row-set parity proof before entering the retirement phase. This verification can keep a read snapshot open on a large backlog. Budget and observe it separately from physical table maintenance.

Run `scripts/deploy/worker-report-staging-keys.sh retire INSTANCE_UUID FULL_SERVING_REVISION`. It drops only the four staging membership indexes concurrently, leaving the covering bootstrap index until last. A subsequent invocation with the same verified revision resumes an interrupted retirement. Concurrent DDL may wait for old database snapshots. The source table, scheduling records, signed reports, result payloads, conflicts, science, receipts and seven other source indexes keep their existing ownership. After retirement the candidate view reads the narrow indexes. Broad-source parity verification requires restoration of the covering source index.

Run `scripts/deploy/worker-report-staging-keys.sh restore INSTANCE_UUID` before switching back to source reads or deploying older reader code. It recreates missing or interrupted source indexes concurrently in reverse retirement order, verifies the resulting definitions and membership, and leaves the current reads active. When the state is `present`, `disable INSTANCE_UUID` switches the view back. Rebuilding the original JSON-expression predicates may take substantial time on a worker with large inline reports. Use the separate rewrite guard for any later physical table rewrite.

## What remains authoritative

- A status report with an absent, scalar or JSON-null result has no staging key. The final-stop predicate also recognizes some no-result cancellations. Its separate source index and callers keep that behavior.
- Per-job claims select the immutable body by the key and recheck its acknowledgement. Wake and priority queries still apply their existing exclusion and ownership rules. Conflict rows and historical-copy coverage affect eligibility for work without rewriting membership.
- The publication index for unacknowledged reports, final-stop index, archive/retention predicates and signed source readers continue to use their own source data. A staging key does not acknowledge delivery, validate raw custody or make an attempt eligible for a polar.


## Workload acceptance

The governed `worker-staging-key-rollout` graph installs the journaled schema on disposable PostgreSQL 16. Its `workload-to-storage` check runs one finite failed URANS workload before and after cutover. It measures source and tracking writes, including first and repeated acknowledgements, unchanged metadata, status-only rows, and normalized representations. It captures per-statement CPU, source TOAST access and key writes.

The worker stages from the signed report and a distinct hub handles the registered requests through Fastify injection. The archive service must hold scientific reports until the returned point receipt matches both stable attempts. The check reloads saved compressed bytes, verifies the pinned generation and all original report text, rejects corrupted bytes, and verifies the failed disposition and numerical evidence through operator rollback. The graph retains a JSON receipt in its workload diagnostics.
